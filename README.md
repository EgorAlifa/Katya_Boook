# Скрипты сборки книги «Вместе с космонавтами»

Пайплайн в **2 шага**. Результат — полностью редактируемый `.docx`: реальные
именованные стили Word, реальное автообновляемое оглавление, реальные формулы
через Word Equation, реальная автонумерация страниц/глав.

## 0. Зависимости
```
pip install python-docx lxml
npm install docx
```
Для проверки сборки (не обязательно для самой генерации): LibreOffice
(`soffice`) + Poppler (`pdftotext`/`pdftoppm`), чтобы отрендерить и глазами
свериться с результатом.

**pandoc и `unzip` больше не нужны** — раньше пайплайн шёл
`pandoc → markdown → регексы`; сейчас `parse_docx.py` читает `.docx` напрямую
через объектную модель Word (`python-docx`), без markdown-прослойки. См.
«Почему не pandoc» ниже.

## 1. parse_docx.py
Один проход по `вар22223333.docx`: читает `document.body` напрямую (абзацы и
таблицы вперемешку, в реальном порядке), для каждого абзаца — реальные raны
текста (bold/italic/subscript-флаги, не markdown `**`/`*`/`~..~`) и реальные
вложенные картинки (`w:drawing`) на их точной позиции в последовательности
ranов. Пишет:
- **`classified.json`** — те же типы блоков, что и раньше (`chapter_mark`,
  `chapter_title`, `subheading`, `task_label`, `answer_label`, `para_dropcap`,
  `para`, `formula`, `image`, `caption`, `callout`, `dashtable`,
  `conclusion_mark`) — `design.js`/`build-full.js` не изменились ни на строку.
- **`img/`** — байты картинок прямо из `document_part.related_parts[...].blob`
  (те же самые байты, что дал бы `unzip`, проверено побайтово), файлы
  называются как в оригинале (`image99.jpeg` и т.д.) — `design.js` смотрит
  на эту папку как раньше.
- **`colophon_lines.json`** — реальный текст колофона книги (см. ниже).

Запуск: `python3 parse_docx.py`

### Почему не pandoc + regex
Предыдущая версия пайплайна шла `pandoc -t markdown → book.md →
parse_book.py → classify_book.py`. За время работы над этой книгой на этом
пути нашлось и было исправлено подряд **семь разных багов**, и все — одной
природы: markdown — плоский текст, а не структура, поэтому реальные
bold/italic/subscript-флаги и точная позиция картинки в потоке текста
терялись или требовали угадывания регулярками:
- `~T~` — pandoc-подстрочник — иногда оставался в тексте буквальными
  тильдами.
- Картинка, приклеенная к своей же подписи без пустой строки между ними
  (`![img]{...}**Рисунок 1-9.** *...*`), в едином markdown-блоке короче 400
  символов целиком принималась за «просто картинку» — подпись **пропадала**
  (нашлось 24 места по книге).
- Картинка, приклеенная в середину предложения, всегда выдёргивалась вперёд
  текста — предложение видимо разрывалось, а подпись рисунка отрывалась от
  самого рисунка (например «Задача 3-7»).
- То же самое с `ОТВЕТ`/буквицей: если картинка стояла прямо перед меткой
  или перед первой буквой абзаца в той же markdown-строке — она тоже могла
  потеряться.
- ASCII-art grid-таблицы (`+---+`) pandoc для врезок «Это интересно»
  разбирались хрупким ручным реконструктором колонок — одна картинка внутри
  такой врезки терялась молча.
- `parse_book.py` изначально **обрезал** книгу на слове «СОДЕРЖАНИЕ» — всё,
  что дальше (настоящий колофон книги: реальный формат печати, тираж,
  типография), уходило в поле `tail`, которое никто не читал; вместо этого
  на странице колофона стоял вручную вписанный текст-заглушка.

`python-docx` читает те же самые факты (bold/italic/subscript, порядок
ranов, вложенные картинки) напрямую из объектной модели — без
сериализации в markdown и обратного разбора, то есть без единой возможности
что-то из этого потерять или угадать неправильно. Все семь багов выше в
`parse_docx.py` физически невозможны как класс ошибок, а не залатаны точечно.

## 2. build-full.js
Не изменился по структуре: `npm install docx`, читает `classified.json`,
режет на сегменты (введение / глава 1/2/3 / заключение), для каждого блока
вызывает нужную функцию из `design.js`, собирает `.docx` через библиотеку
`docx` со стилями/нумерацией/оглавлением-полем. Дополнительно теперь читает
**`colophon_lines.json`** — реальный текст последней страницы книги (имена
авторов, «Формат 60×84 1/8», тираж, адрес типографии) вместо вручную
вписанного текста-заглушки, который стоял раньше. Единственная сознательная
правка реального текста — строка про гарнитуры: в оригинале написано
«Гарнитура Times New Roman» (верно для исходной рукописи), но неверно для
этого издания — заменена на «Literata, JetBrains Mono».

Результат: `book_full.docx`.

Запуск: `node build-full.js`

## design.js
Модуль с «дизайн-системой»: именованные Word-стили (`WORD_STYLES` +
`DEFAULT_STYLES` для Heading1/2, `CHARACTER_STYLES` для номера страницы),
автонумерация глав (`CHAPTER_NUMBERING`), функции-строители параграфов.
Правки кегля/цветов/интервалов — сюда.

Дизайн переверстан под макет-эталон (`вар 3 (1).pdf`) и бриф-промт на
исправление вёрстки: единый акцентный navy вместо разделённых
navy/blue/orange, единственный текстовый шрифт (Literata) вместо пары
body/heading, формат A4 вместо самопального 200×290мм.

## Редактируемость
- **2 шрифта**: Literata (`FONT_BODY`, весь текст — от заголовков до
  подписей и титульного листа), JetBrains Mono Medium (`FONT_MONO`,
  ЗАДАЧА/ОТВЕТ, «ЭТО ИНТЕРЕСНО», номера страниц, технические строки
  титула/колофона — никогда не основной текст).
- **Палитра — 7 фиксированных цветов, без единого оттенка оранжевого**:
  Navy `#1B2952` (единственный акцент — заголовки, буквица, ЗАДАЧА/ОТВЕТ,
  линии, номер страницы), Ink `#232118` (основной текст), Gray `#666666`
  (подписи, колонтитул), Light Gray `#999999` (технические строки/имприт),
  Subtitle Gray `#54534B` (подзаголовок на титуле), Callout Text `#3A372F`
  (текст врезки «Это интересно»), Paper `#F7F6F2` (только заливка врезки —
  не фон страницы).
- **Настоящие именованные стили Word**, все — `REF-*` (кроме `Heading1`/
  `Heading2`, чьи id фиксированы форматом `heading:`, но чьё отображаемое
  имя в палитре стилей Word тоже переименовано в `REF-Chapter`/
  `REF-Question` — см. ниже): `REF-Title`, `REF-Subtitle`, `REF-Authors`,
  `REF-Technical`, `REF-Body`, `REF-FirstParagraph`, `REF-Caption`,
  `REF-Task`, `REF-Answer`, `REF-Info`, `REF-Formula`, `REF-TableLabel`,
  `REF-Header`, плюс символьный (character) стиль `REF-PageNumber` — правка
  стиля в Word каскадируется на все его инстансы.

  ⚠️ **При правке `design.js` никогда не указывайте одновременно
  `style: "..."` и `heading: HeadingLevel...`** в одном параграфе — `heading:`
  сам навешивает встроенный стиль Word, и повторный `style:` добавит ВТОРОЙ
  `<w:pStyle>` в XML — это ломает распознавание заголовков для автооглавления
  (проверено: оглавление после такой ошибки строится пустым). Для параграфа
  со своим стилем, который всё же должен попасть в оглавление — задайте у
  стиля `outlineLevel` вместо `heading:` (см. `questionHeading()`/стиль
  `Question`).

  ⚠️ **Не добавляйте `Heading1`/`Heading2` в `WORD_STYLES`** — docx.js
  всегда сам генерирует встроенные стили `Heading1`..`Heading6` через
  `DefaultStylesFactory`, независимо от `paragraphStyles`; если добавить
  туда ещё и свою запись с тем же `id`, в `styles.xml` окажутся ДВА
  `<w:style styleId="Heading1">` подряд — проверено побайтово. Word,
  видимо, берёт последний, а LibreOffice — первый (родной синий стиль без
  наших правок), из-за чего в headless-рендере заголовки выглядели синими
  и левыми вместо navy и по центру. Правильное место для переопределения
  Heading1/2 — `styles.default.heading1`/`heading2` (экспортируется из
  design.js как `DEFAULT_STYLES`, см. `IDefaultStylesOptions` в
  `node_modules/docx/dist/index.d.cts`); он же принимает `name`, так что
  здесь и переименовываются отображаемые имена в `REF-Chapter`/
  `REF-Question` без потери id, на который опирается `heading:`.

  ⚠️ **Формулы (`Math`/`MathRun`/`MathFraction`) не красятся и не
  перешрифтовываются** — конструктор `MathRun` в docx.js принимает только
  голый текст (`constructor(text: string)`), без `run`-опций цвета/шрифта;
  OMML-контент рендерится текстовым движком формул Word/LO своим
  умолчанием (в LO — чёрным, `LiberationSerif`), а не через `w:rPr`
  окружающего параграфа. Формула при этом остаётся настоящим редактируемым
  Word Equation — просто её цвет средствами этой библиотеки не задать;
  чтобы всё-таки покрасить/сменить гарнитуру формулы в navy/JetBrains Mono,
  нужно вручную собирать OMML `m:rPr` в обход docx.js.
- **Оглавление** — настоящее поле Word (`TableOfContents`), не текст.
  Пересчитывается само при открытии (`features.updateFields: true`) или
  через References → Update Table.

  ⚠️ Проверка headless-конвертацией LibreOffice (`soffice --convert-to pdf`)
  показывает оглавление пустым или не полностью переразбитым на страницы —
  это ограничение headless-экспорта LO, а не баг документа: через
  `doc.getTextFields().refresh()` + `getDocumentIndexes()` в UNO-скрипте LO
  подтверждено, что поле находит все реальные заголовки и верные номера
  страниц. В настоящем Word (для которого и делается документ) поле
  разворачивается нормально при открытии.
- **Формулы** — настоящие Word Equation (`Math`/`MathFraction`/`MathRun`),
  не скриншоты.
- **Формат страницы: A4 (210×297 мм), поля ~2 см со всех сторон** — задано
  бриф-промтом на исправление вёрстки (раньше здесь стояло 200×290мм,
  выведенное из колофона источника — «Формат 60×84 1/8»; тот факт остаётся
  верным для типографской печати книги, но вёрстка этого `.docx` теперь
  сознательно ведётся под стандартный A4).
- **Номера страниц** — `PageNumber.CURRENT`, настоящее поле Word, в
  колонтитуле сверху справа, стиль `REF-PageNumber` (JetBrains Mono
  Medium, navy).
- **Колонтитулы** — сверху только название раздела (слева) + номер
  страницы (справа), никакого названия книги; снизу — полностью пусто.
  Это сознательное отличие от эталонного PDF (там колонтитулы устроены
  иначе), см. `makeHeader()`/`makeFooter()`.

## Что чаще всего нужно менять
- **Кегль/интервалы текста** → `design.js`, стиль `REF-Body`/
  `REF-FirstParagraph` в `WORD_STYLES`.
- **Цвета/шрифты вообще** → `design.js`, константы в самом верху файла.
- **Размер/поворот картинок** → идут в размере и повороте **из оригинального
  docx** (`wp:extent`/`a:xfrm/@rot`, читается `parse_docx.py` напрямую, без
  отдельного шага). `figureParagraph()`/`figureRow()` принимают
  `maxWidthIn`/`maxHeightIn` только как аварийный потолок на случай
  переполнения полосы — не как целевой размер, и `imgDimsNative()` не
  уменьшает картинку более чем на 15% от её собственного объявленного
  размера (`MIN_SCALE`).
- **Оформление задач/ответов/вопросов** → `design.js`, стили `REF-Task`/
  `REF-Answer`/`REF-Question` (последний — переопределение `Heading2` в
  `DEFAULT_STYLES`, не запись в `WORD_STYLES`, см. предупреждение выше).
- **Формат страницы/поля** → `design.js`, константы `PAGE_W`, `PAGE_H`,
  `MARGIN_*` (в твипах, 1440 = 1 дюйм).
